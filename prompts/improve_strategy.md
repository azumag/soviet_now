    """
    Args:
        game_state: {"state", "score", "next": {"type", "r"}, "nextNext": {"type", "r"},
                     "pieces": [{"id", "type", "x", "y", "r", "vx", "vy", ...}], "shapes": {...}}

## ★★★ 最重要0: 同じ改善を繰り返すな ★★★

**改善の第一歩は、過去の変更履歴を読み、自分が堂々巡りしていないか確認することである。**

### 反復検出（必ず最初に実行せよ）

strategy.py 冒頭の `# --- 変更履歴 ---` を全て読み、以下をチェックせよ:

1. **振り子パターン**: 「Aを削除」→「Aを再導入」→「Aを削除」のように同じ要素を追加・削除・再追加していないか？
   - 例: 「危機回避閾値1.2→1.5」→「危機回避閾値1.5→1.2」
2. **閾値シャッフル**: 同じパラメータの閾値を微調整し続けていないか？（90%→95%→90%→95%...）
3. **名前変え再発明**: 本質的に同じロジックを別の名前で何度も導入していないか？

### 振り子を検出した場合 → ブレイクスルーが必要

過去の履歴で振り子パターンを発見したら、**その要素の追加も削除もするな**。代わりに:

1. **なぜ振り子が起きるか根本原因を考えよ**: 「削除するとスコアが下がる、でも存在すると別の問題が起きる」なら、その要素自体ではなく**周囲の設計が悪い**
2. **第三の選択肢を考えよ**: AかBかではなく、AもBも不要になるような全く別のアプローチを探せ
3. **抽象度を上げよ**: 個別のif分岐ではなく、スコアリング関数の重み付けなど、より一般的な仕組みで解決できないか？
4. **その要素が本当にスコア向上に必要か、履歴データで確認せよ**: 発動時のscore_deltaが正なら有効、0なら無駄

## ★★★ 最重要1: 既存戦略を疑え ★★★

**改善とは閾値の微調整ではない。既存の戦略構造そのものを疑うことである。**

### 改善の優先順位
1. **反復していないか確認が最優先**: 上記の反復検出を必ず最初に行え
2. **構造レベルの戦略改善が次に優先**: ロジックの追加・削除・統合・書き直しなど、戦略の構造を変える改善を第一に考えよ
3. **閾値の微調整は補助手段**: 閾値調整は禁止しないが、それだけで終わらせるな。構造改善と組み合わせて初めて意味がある

### 禁止事項
1. **コピペ追記禁止**: 既存ロジックをそのまま残して新しいif分岐を追加するだけの変更は禁止。既存ロジックの削除・統合・書き直しを恐れるな
2. **ファイル管理はスクリプトが担当**: 戦略バージョンの保存・削除・殿堂入り・変更履歴のトリミングは全てスクリプト側で自動実行される。AIは strategy.py の中身の改善だけに集中せよ

### やるべきこと（構造レベルの改善）
1. **「このロジックは本当に必要か？」を全ブロックに問え**: 特にif分岐が5段以上ネストしているロジック、到達率が低そうな分岐、互いに矛盾する条件は削除候補
2. **decision_reason の分布を分析せよ**: 履歴のdecision_reasonを集計し、最も多い理由が「マージ」以外なら、その戦略が支配的すぎる。支配的な非マージ戦略は弱体化または削除を検討せよ
3. **履歴のdecision_reasonとscore_deltaの相関を分析せよ**: どの理由でドロップした時にスコアが伸びたか？伸びなかったか？データに基づいて戦略を取捨選択せよ
4. **全く新しいアプローチを試せ**

### 改善の思考プロセス
```
1. 履歴分析 → 「何が悪かったか」ではなく「どのロジックが悪さをしたか」を特定
2. そのロジックの存在意義を疑う → 本当に必要？削除したらどうなる？
3. 履歴データで、そのロジック発動時のscore_deltaは正だったか？ → 0以下なら不要
4. ロジックを削除 or 根本的に書き直し → 閾値微調整は最終手段
```

## 分析→改善の手順

2. **最終盤面分析**: game_state.json

4. **改善実装**: strategy.py の decide() を改善

## 改善のヒント

### 使える情報
- `game_state["pieces"]`: 全ピースの位置・type・速度
- `game_state["next"]`/`game_state["nextNext"]`: 次と「次の次」のピース
- `analysis["results"]`: 全サンプルX座標の物理的事実（着地Y、マージグレード、ドリフト等）。スコアリングは含まれないので decide() 内で自由にスコアリング関数を設計できる
- `analysis["results"][N]["merges"]`: 各同typeピースへのマージ情報（距離、グレード、接触距離）
- `analysis["reactor"]`: 盤面状態（同typeペア距離、パイプライン健全性）
