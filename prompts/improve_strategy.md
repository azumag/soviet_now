## strategy.py のインターフェース契約（変更禁止）

```python
def decide(game_state: dict, analysis: dict) -> dict:
    """
    Args:
        game_state: {"state", "score", "next": {"type", "r"}, "nextNext": {"type", "r"},
                     "pieces": [{"id", "type", "x", "y", "r", "vx", "vy", ...}], "shapes": {...}}
        analysis: {"results": [{x, landing_y, drift_x, drift_unc, merge_grade, has_merge, merges}],
                   "same_type": [{id, type, x, y, r}],
                   "reactor": {type_count, reactive_pairs, near_pairs, pipeline, ...}}
    Returns:
        {"x": float, "reason": str}  # x は -3.0〜+3.0

    NOTE: analysis["results"] には
    物理的事実（着地Y、マージグレード、ドリフト等）のみ提供される。
    スコアリング・評価ロジックは decide() 内で自由に設計すること。
    """
```

## 参照データの読み方

以下のファイルがこのプロンプトに埋め込まれている。加えて、`sorengame/` 以下のゲームソースコードも必要に応じて読むことができる。

改善対象の decide() ロジック。

### 2. batch_summary.txt (直近の試合統計サマリー)
試合の横断分析（1試合〜複数試合）。以下を含む:
- スコア統計 (min/max/avg/median/stddev)
- decision_reason の全体分布と avg_score_delta
- 高スコア群 vs 低スコア群の比較（reason分布・merge_rate・max_y推移の違い）

### 3. ベストゲーム/ワーストゲームの詳細JSONL (各1試合)
最高スコア試合と最低スコア試合のターン履歴（1試合のみの場合は同一）。
各行がJSON: `{"turn", "score", "score_delta", "piece_count", "max_y", "next_type", "decision_x", "decision_reason", "merge_available", "best_merge_grade", "reactor_reactive_pairs", ...}`
この2試合を対比して「何が違ったか」を分析せよ。

### 4. game_state.json (最終盤面)
ゲームオーバー時の盤面。散在・到達不能ピースの分析に使用。

### 5. 直近10バージョンの戦略 (strategy_versions/v*_strategy.py)
過去の strategy.py。スコアがファイル名に含まれる（例: v005_score1200_strategy.py）。
どのバージョンが高スコアだったか比較し、良かった戦略の要素を取り入れ、悪かった変更を避けよ。

### 6. 殿堂入り戦略 (strategy_versions/best_score*_strategy.py)
ハイスコア達成時の strategy.py。スコアがファイル名に含まれる。
最も成功した戦略構造の参考にせよ。ただし盲目的にコピーするな。なぜそれが高スコアだったかを分析し、本質的な要素だけを取り入れよ。

## ★★★ 最重要0: 同じ改善を繰り返すな ★★★

**改善の第一歩は、過去の変更履歴を読み、自分が堂々巡りしていないか確認することである。**

### 反復検出（必ず最初に実行せよ）

strategy.py 冒頭の `# --- 変更履歴 ---` を全て読み、以下をチェックせよ:

1. **振り子パターン**: 「Aを削除」→「Aを再導入」→「Aを削除」のように同じ要素を追加・削除・再追加していないか？
   - 例: 「危機回避閾値1.2→1.5」→「危機回避閾値1.5→1.2」
2. **閾値シャッフル**: 同じパラメータの閾値を微調整し続けていないか？（90%→95%→90%→95%...）
3. **名前変え再発明**: 本質的に同じロジックを別の名前で何度も導入していないか？

### 振り子を検出した場合 → ブレイクスルーが必要

過去の履歴で振り子パターンを発見したら、**その要素の追加も削除もするな**。代わりに:

1. **なぜ振り子が起きるか根本原因を考えよ**: 「削除するとスコアが下がる、でも存在すると別の問題が起きる」なら、その要素自体ではなく**周囲の設計が悪い**
2. **第三の選択肢を考えよ**: AかBかではなく、AもBも不要になるような全く別のアプローチを探せ
3. **抽象度を上げよ**: 個別のif分岐ではなく、スコアリング関数の重み付けなど、より一般的な仕組みで解決できないか？
4. **その要素が本当にスコア向上に必要か、履歴データで確認せよ**: 発動時のscore_deltaが正なら有効、0なら無駄

## ★★★ 最重要1: 既存ロジックをむやみに削除するな ★★★

**改善とは「既存コードを削除してシンプルにすること」ではない。**

### 削除のルール
- 既存ロジックの削除は、**そのロジックがスコアを下げているデータ的根拠がある場合のみ**許可する
  - 例: decision_reasonのavg_score_deltaが負、そのロジック導入後にスコアが一貫して下がった等
  - 削除する場合は変更履歴に根拠データを必ず記載せよ
- **根拠なく「シンプルにしたほうが良い」という理由での削除は禁止**
- **既存コードを丸ごと書き直して短くするのは禁止**。「アルゴリズム全体を刷新する」という名目でうまくいっていた戦略を捨ててはならない
- **「最近のN回の改善が全て失敗した → 元のロジックが根本的に間違っている → 削除してシンプル化しよう」は禁止**。最近の改善が失敗したのは追加した部分の問題であり、元からあった土台ロジック（フェーズ判定、高度ペナルティ、バランス補正等）の問題ではない。失敗した追加分を取り除くのはOKだが、それ以前から存在していた土台まで削除するな

### 改善の基本方針: 追加・拡張を優先せよ
- 既存のスコアリング構造に新しい要素を追加する形が基本
- 既存ロジックの置き換えより、新しいボーナス/ペナルティの追加を優先せよ
- コードが長くなることを恐れるな。短いコード≠良い戦略

### 具体的なNG例
- 150行のdecide()を50行に「改善」する → うまくいっていたロジックが失われている
- 「このロジックは効果が薄いので削除」→ データの裏付けなしの削除
- フェーズ判定(LOW/MEDIUM/HIGH/CRITICAL)を削除して単純なif文にする → 根拠なき簡略化

### 禁止事項
1. **パラメータ微調整の禁止**: 既存のスコアリング係数（マージボーナス値、height_mult、ペナルティ倍率など）の数値を変えるだけの変更は**禁止**。1500→1600、1.7→1.8のような変更は改善ではない。アルゴリズム自体を変えよ
2. **コピペ追記禁止**: 既存ロジックをそのまま残して新しいif分岐を追加するだけの変更は禁止。ただし、機能しているロジックを「シンプルにする」目的で削除するのも禁止。削除は「そのロジックがスコアを下げている」というデータに基づく場合のみ許可
3. **ファイル管理はスクリプトが担当**: 戦略バージョンの保存・削除・殿堂入り・変更履歴のトリミングは全てスクリプト側で自動実行される。AIは strategy.py の中身の改善だけに集中せよ

### やるべきこと: アルゴリズムレベルの改善
既存の戦略構造を活かしつつ、以下のような新しいアプローチを取り入れよ。既存ロジックを削除する場合はデータに基づく根拠が必要だが、新しい要素の追加は自由に行ってよい:

1. **クラスタリング戦略**: 盤面のピースをtype別にクラスタリングし、同typeが近い「マージ予備軍クラスタ」を識別。新ピースはクラスタを強化する位置に落とす。散在ピースが多いならクラスタに寄せることを優先
2. **マージチェーン予測**: 「type Nを2個マージ → type N+1が生まれる → 既存のtype N+1と接触 → 連鎖マージ」という連鎖を盤面から探索し、連鎖が長くなる位置を優先。スコアは `1+3+6+10+...` と加速度的に増えるので、高typeの連鎖は低typeの単発マージより圧倒的に価値が高い
3. **盤面密度マップ**: ボードを格子に区切り、各セルのピース密度・type分布を分析。過密領域を避け、同typeが隣接する低密度領域に落とす
4. **重力シミュレーション活用**: 小ピース(type1-5)は質量200-160で重く、大ピース(type12-16)は質量40-10で軽い。小ピースを大ピースの上に落とすと振動で盤面が動く。これを意図的に利用して「振動マージ」を狙う位置選択
5. **ゾーン管理戦略**: ボード左半分と右半分で異なるtype帯を育てる。左は低type集約、右は高type集約のように分離し、マージ効率を上げる
6. **パイプライン最適化**: 現在のpipeline健全性（reactor情報）を分析し、マージチェーンが途切れている箇所（あるtypeが0個で次のtypeが2個以上ある等）を特定。途切れ箇所を埋めるtypeが来たらそこに優先配置
7. **爆発力活用**: マージ時に半径2ユニット・450Nの爆発力が発生する。この爆発で他のピースが移動してさらにマージが起きる可能性がある。既存の同typeペアの近くでマージを起こし、爆発の波及効果で連鎖を狙う
8. **ゲームオーバー回避**: デッドラインy=3.32で5秒、y=4.16で2秒触れるとゲームオーバー。盤面高さが危険域に近いとき、単に「低い位置に置く」のではなく、マージで盤面を下げることを最優先する

### 改善の思考プロセス
```
1. 履歴分析 → 「どの状況でスコアが伸びたか/詰んだか」のパターンを特定
2. 現在のアルゴリズムの限界を特定 → このアルゴリズムでは原理的に捉えられない状況は何か？
3. 上記の戦略候補から、その限界を突破できるアプローチを選択
4. 既存の戦略を土台に、新しいロジックを追加・拡張する
   ※ 既存ロジックの削除はデータ根拠がある場合のみ
```

## 分析→改善の手順

1. **試合の傾向分析**: batch_summary.txt から

   - decision_reason の分布と avg_score_delta の相関（どの判断が効果的か）
   - 高スコア群 vs 低スコア群で何が違うか

2. **ベスト vs ワーストの対比**: 詳細JSONL 2試合を比較

   - 盤面の高さ推移(max_y)の違い
   - merge_available 率の違い

3. **構造的問題の特定**: strategy.py のロジック構造を批判的に分析
   - バッチデータが示す「効果のない判断」に対応するロジックはどれか
   - 互いに矛盾・重複する条件はないか
   - 情報を十分に活用しているか

4. **改善実装**: strategy.py の decide() を改善
   - 既存の戦略を土台に、新しいロジックを追加・拡張する（行数が増えても構わない）
   - 既存ロジックの削除はデータ根拠がある場合のみ。根拠なく「シンプル化」しない

## 改善のヒント

### 使える情報
- `game_state["pieces"]`: 全ピースの位置・type・速度
- `game_state["next"]`/`game_state["nextNext"]`: 次と「次の次」のピース
- `analysis["results"]`: 全サンプルX座標の物理的事実（着地Y、マージグレード、ドリフト等）。スコアリングは含まれないので decide() 内で自由にスコアリング関数を設計できる
- `analysis["results"][N]["merges"]`: 各同typeピースへのマージ情報（距離、グレード、接触距離）
- `analysis["reactor"]`: 盤面状態（同typeペア距離、パイプライン健全性）

### ゲーム物理の正確な仕様（Unityソースより）

**スコアテーブル** (マージ元のtypeで決まる。N+N→N+1のマージでscore[N]点を獲得):
type1=1, type2=3, type3=6, type4=10, type5=15, type6=21, type7=28, type8=36, type9=45, type10=55, type11=66, type12=78, type13=91, type14=105, type15=120
→ 高typeマージほど圧倒的に高得点。type15マージ(120点)はtype1マージ(1点)の120倍。**低typeの最適化に時間を使うのは非効率**

**質量** (小さいほど重い！):
type1=200, type2=190, type3=180, ..., type8=110, ..., type12=40, type13=30, type14=20, type15=15, type16=10
→ type1はtype16の20倍重い。小ピースは沈み、大ピースは浮く

**マージ判定**: 距離閾値ではなく**Unity物理エンジンの衝突判定**(OnCollisionEnter2D)。同type同士が物理的に接触すればマージ発生
**マージ時爆発**: 半径2ユニット、450Nの衝撃波。周囲のピースを吹き飛ばし、連鎖マージを誘発する
**マージ位置**: 2ピースの中点に新ピースが生成される

**ボード**: x: ±3.2, 床y=-4.48, デッドラインy=3.32(5秒でゲームオーバー), y=4.16(2秒でゲームオーバー)
**出現ピース**: type1-11のみがランダム出現(均等確率)。type12-16はマージでのみ生成
**ドロップ後1秒で次のピースが操作可能になる**

**戦略的含意**:
- 高typeマージの連鎖を狙うのが最も効率的（スコアは加速度的に増加）
- 小ピースを大ピースの上に落とすと、重さで振動が起き、盤面が動いてマージが誘発される
- マージ時の爆発(450N)で周囲のピースが移動し、さらにマージが連鎖する可能性がある
- 大ピースは軽くて浮きやすい → 大ピースの上に小ピースで「蓋」をする戦略が有効
- これらの振動・連鎖効果は `analysis["results"]` の着地Y予測には反映されないため、decide() で独自に考慮する必要がある

### 先読みマージ戦略（重要）
- **next/nextNextの「マージ先予約」**: nextがtype Nなら、盤面にtype N-1のペアがあるか確認せよ。もしtype N-1が2個以上あれば、いずれマージしてtype Nが生まれる。その場所の近くに今のnext(type N)を置けば、将来の連鎖マージが狙える
- **nextNextも同様**: nextNextがtype Mなら、盤面のtype M-1ペアの近くに今のピースを置くことで、次のターンでnextNextを連鎖マージしやすい位置に誘導できる
- **期待値的思考**: 単に「今マージできるか」だけでなく、「この位置に置いたら将来マージが起きる確率はどうか」を考えよ。盤面のtype N-1ペアの数・距離・位置から、将来マージが起きる期待値を計算し、スコアリングに反映せよ
- **具体的な実装例**: `pieces` から type N-1 のピースを抽出し、それらが近接していれば「マージ予備軍」として、その重心付近にボーナスを付与する。`analysis["reactor"]["near_pairs"]` や `analysis["reactor"]["reactive_pairs"]` にはtype N-1同士のペア情報も含まれているので活用せよ
