# v770 LADDER_STACK：小さい駒を上・大きい駒を下に積む

## 何が天井だったか（実測 2026-10-25）

本番 120 試合（約 11,000 手）とゲーム本体（`MainManager.GetRandomNext()`）から確認した。

- 落下ピースは type 1〜11 の一様分布（各 8〜10%）。小型だけが降るスイカゲームとは違う。
- 併合機会（解析器 DIRECT）は全手の 28%。機会があれば 97% 取れており、取りこぼしは律速ではない。
- 表面の露出駒は盤面の大きさによらず約 3.7 個・3.6 種で、機会率 ≈ 露出型数 / 11。
  表面はすでにほぼ全部が別の型で、多様性（v763）を上げる余地はない。**天井は表面の枠数と連鎖の短さ**。
- 併合が起きた手の連鎖は 1 回で終わるのが 70%（平均 1.54 回）。
- 終局盤面は平均 41 駒、そのうち 28 駒は「同型が盤上にあるのに接触できない」駒。
- 2026-08-31 以降、週次の score 平均は 1,790〜1,880、併合/手 0.55〜0.56 で横ばい。

## 人手の勝ち筋との一致

`docs/manual_challenge_20260825_insights.md` §3 の「縦積みラダー」（同型ペアを一つ大きい型の
真上に組み、1 回の直撃で 3〜5 連鎖させる）を、本番ログで測り直した（非併合手のみ、20 手追跡）。

| 置いた駒の真下 | その駒がのちに併合したときの連鎖 |
|---|---|
| T+1（ラダー） | 2.74〜3.23 回（サイズ帯ごと） |
| その他の駒 | 約 2.3 回 |
| 床 | 約 1.5 回 |

- 露出した T+1 がある非併合手は 43% あるが、実際に T+1 へ載せたのは 8%。
- 露出した小型（T1〜4）を 2 段以上大きい駒で覆うと、その小型が 20 手以内に併合される率は 29%。
  小さい駒が上に載った場合（ラダー）は 54%。T5〜8 でも 37% 対 48%。

区画分け（表面の枠を増やす）と梯子配置（連鎖を伸ばす）は、どちらも
「小さい駒を上・大きい駒を下に積む」という同じ原則にまとまる。

## 実装

`_decide_base` の候補ループの最後（安全条件は v748 SEAT_LANES と同じ。非併合・締切非超過・
余裕 1.0 以上・壁回転なし・death spiral なし・ロシア前）に 2 つの項を足す。

1. **LADDER_STACK**：解析器の `landing_hit_id` が、上の空いた T+1（`_v742_open_twin` と同じ判定）で、
   落下 x が T+1 の中心から水平半径の 0.5 以内なら `+600 × (1 − ずれ)`。
   その T+1 が T+2 の上に載っていれば（2 段のラダー）さらに +150。
2. **INVERTED_BURIAL**：`landing_hit_id` が、上の空いた T1〜min(8, T−2) の駒なら −250。

同型相方を狙う既存軸が働く盤面では、どちらの項も付けない（`_v770_defer`）。
上端の開いた同型相方がある盤面（v736 PROBABLE_MERGE_CONTACT、最大 +800）と、T9 以上で同型相方がある盤面
（v731 SAME_TYPE_SEED_CONTACT、最大 +400）が対象。最初の版はラダー加点（+600）と下敷き減点（−250）が
これらの候補を押しのけていた（実盤面 `probable_merge_t8_turn41` / `seed_contact_t11_turn15`）。

中心付近に限るのは、`landing_hit_id` が T+1 でも中心から半径 0.25 以内なら 61% が実際に
T+1 の上に止まるのに対し、0.8 超では 13% しか止まらない（肩で転がり落ちる）ため。

重みはモジュール定数 `_V770_LADDER_W = 1.0`（0 で従来と完全一致、上限 4）。env では切り替えない。

### 重みを env で読まない理由（2026-10-25 実測）

候補の AST deny gate（`strategy/sandbox.sh`）は `import os` を禁じている。稼働中の root だけは
信頼済みとして gate を通さないため、root の `_v763_weight()` は `os.environ` を読めていた。
一方、LLM 候補（3fedf0802964 / ac52cd600115）は `import os` を削り、`_v763_weight()` を `return 0.0` に
書き換えて gate を通していた。本番 `.env` は `V763_DIVERSITY_W=1.0` なので、LLM 候補の B 腕では
v763 が黙って無効になっていた。v770 の最初の版も同じ理由で A/B 開始時に gate で拒否された。

そこで v763 の重みも本番値 `_V763_DIVERSITY_W = 1.0` を定数で持つ。本番の挙動は変わらない。
この root から派生する候補は os を削っても v763 を失わない。`.env` の `V763_DIVERSITY_W` は、
定数化した root が採用された後は読まれない。

## オフライン検証（本番 120 試合から 2,500 手を再生、root は `V763_DIVERSITY_W=1.0`）

- 再生器は記録された手の 87.8% を ±0.2 以内で再現する。
- `_V770_LADDER_W = 0` は root（853ae5ebd7e8）と 2,500 手すべてで x と reason が一致。
- 有効時に手が変わるのは 213 手（8.5%）。安全で中心に載れるラダー機会 387 手のうち、
  ラダーを選ぶ手は root 79 手（20%）→ 候補 193 手（50%）。
- 変わった手の締切超過は root 0 手・候補 0 手、余裕 1.0 未満は 12 → 10 手。
  ただし縦に積むぶん、変わった手の 1 割は余裕が 1.1 以上縮む（実戦 A/B の害停止で見る）。
- 本番設定（V763=1）で走らせた戦略系テストの失敗集合は、root と候補で一致する（v770 による新規失敗なし）。
  CI 対象外の旧固定値テスト 11 件（接触・播種系）は V763=0 前提で書かれており、本番設定では root でも落ちる。
- INVERTED_BURIAL の減点は候補ごとの危険フラグ（締切超過・壁回転）で外さない。最初の版は
  加点と同じ条件で外していたため、危険な候補ほど減点を免れて浮く手が実盤面で出た。

オフライン再生は機構の確認であり、成績の改善は実戦 A/B でしか判定できない。
